## **三、正文**

## **3.1 开篇：为什么具身智能必须先学仿真**

### 3.1.1 一个看似简单的问题

让机械臂抓起桌上的杯子，或者让 G1 人形机器人稳定地向前走两步——这些任务，人类看一眼就能做到，为什么不能让机器人直接在真机上试？

答案藏在四个字里：**试错成本**。

假设你写了一段机械臂控制代码，想让末端从当前位置移动到目标点。如果直接在真机上运行：

- **成本高**：一次碰撞可能损坏机械臂关节、夹爪或传感器，维修费用从几千到几万不等。对于 G1 这样的大型人形机器人，一次摔倒的维修成本可能是六位数。
- **风险高**：机械臂高速运动时如果路径计算错误，可能伤及周围人员或设备。G1 如果在行走测试中失控，后果更加严重。
- **难重复**：真机实验中，光照、物体摆放、电机温度、电池电压每天都在变。今天的成功，明天未必能复现。对于需要对比实验的科研工作来说，这种不可控性是致命的。
- **难大规模采样**：强化学习可能需要数百万次试错。即使每次尝试只需 5 秒，一百万次就是约 58 天——这还不算复位、冷却和维护时间。

这四个问题加在一起，给出了一个清晰的结论：**真机是最终验证的手段，不应该是探索和试错的主战场**。

### 3.1.2 仿真解决什么

仿真环境在这四个维度上提供了根本性的解决方案：

| 维度 | 真机直接试错 | 仿真先验证 |
|---|---|---|
| 成本 | 硬件损坏、维修费用高 | 几乎为零的硬件成本 |
| 风险 | 伤人或损坏设备 | 零物理风险 |
| 可重复性 | 环境不可控，难以复现 | 完全可控的初始状态和参数 |
| 采样效率 | 受限于物理时间 | 可并行加速，GPU 上数千环境同时跑 |

但仿真最大的价值不是"省钱"或"省时间"——而是**让问题变得可见**。在真机上，你能看到的只有最终结果：抓住了还是没抓住，站稳了还是摔倒了。在仿真里，你可以看到关节力矩是否异常、接触力是否过大、轨迹哪里开始偏离、摔倒前是哪只脚先失稳。这种"透明性"对于初学者建立直觉来说，是不可替代的。

### 3.1.3 本讲的定位

关于仿真，网上有大量的安装教程和 Demo 视频。本讲不走这个路线。这不是一篇"如何安装 MuJoCo"或"Isaac Lab 第一个例子"的教程。

本讲的核心问题是：**一个真实的机器人操作任务，如何被正确地"翻译"成一个仿真任务？**

围绕这个问题，本讲将带学生走完一条完整的认知链路：
1. 先把真实任务拆成七个必须回答的问题（3.3 节）
2. 再理解不同平台各自擅长回答哪一类问题（3.4 节和 3.5 节）
3. 然后在 MuJoCo 里看模型的骨架和物理参数（3.6 节）
4. 在 Isaac Lab 里看机器人学习环境的组织方式（3.7 节和 3.8 节）
5. 最后回到真实世界，理解仿真和真机之间的差距（3.9 节）
6. 并学会如何把每一次失败变成下一次实验的起点（3.10 节）

**本节小结**：仿真不是为了让机器人"看起来会动"，而是为了让任务可训练、可测试、可评测、可复盘。它不是真机的廉价替代品，而是一个让问题变得可见、让失败变得可分析的认知工具。本讲的终点不是"会跑 Demo"，而是"能解释为什么 Demo 失败"。

## **3.2 任务总览：本讲贯穿的两个任务**

知道了为什么不能直接上真机之后，我们先选两个贯穿本讲的任务：**机械臂操作**和 **G1 locomotion**。选这两个任务不是随机的——它们分别代表了具身智能的两大类问题：操作（manipulation）和运动（locomotion），也分别对应了本讲的两条仿真技术路线。

### 3.2.1 任务 A：机械臂 reach / pick-place

**Reach（到达）** 是最简单的操作原语：控制机械臂末端执行器，从当前位姿移动到指定的目标位姿。看似简单，但它是所有复杂操作的基础。在 reach 中，我们希望学生观察到：
- 末端轨迹是否平滑，还是存在抖动和过冲？
- 是否能稳定收敛到目标点，还是来回振荡？
- 轨迹规划在关节空间和笛卡尔空间的区别是什么？
- 接近目标时的速度曲线如何影响最终精度？

**Pick-place（抓取-放置）** 在 reach 的基础上增加了与物体的物理交互：
- 夹爪何时闭合？闭合力多大？
- 是否真正抓起了物体（而不是推走了它）？
- 抓取过程中物体是否有滑动？
- 放置时物体是否稳定地停在目标位置？
- 如果换一个摩擦力更小或质量更大的物体，结果会变吗？

### 3.2.2 任务 B：G1 standing / walking / turning / disturbance recovery

G1 人形机器人的运动任务与机械臂操作有本质区别：操作任务关注的是**末端和物体**之间的关系，运动任务关注的是**全身姿态和地面接触**之间的关系。

**Standing（站立）**：
- 目标是保持直立姿态，维持零速度。
- 观察点：base 姿态是否稳定、关节是否有高频抖动、足底接触力是否均匀。

**Walking（行走）**：
- 输入一个速度指令（base velocity command），例如"以 0.3 m/s 向前走"。
- 观察点：实际速度是否跟踪上指令速度、步态是否自然、脚底是否打滑。

**Turning（转向）**：
- 输入一个角速度指令，观察机器人如何协调双腿完成转向。
- 观察点：身体是否倾斜、转向半径是否合理、内侧脚和外侧脚的步幅是否协调。

**Disturbance recovery（扰动恢复）**：
- 在站立或行走中施加外部推力，观察机器人是否能恢复平衡。
- 观察点：恢复时间、是否摔倒、恢复策略（迈步还是踝关节补偿）。

### 3.2.3 两个任务的共同点

尽管机械臂操作和 G1 locomotion 看起来完全不同，但在仿真层面，它们需要回答的是同一组问题：
1. 机器人模型是什么？（关节、连杆、碰撞体、质量、惯量）
2. 场景是什么？（地面、桌面、物体）
3. 机器人能看到什么？（关节状态、末端位姿、物体位置、base 姿态）
4. 机器人能输出什么？（关节控制、末端控制、速度指令）
5. 物理参数是什么？（摩擦、质量、接触、控制频率）
6. 成功如何判断？（误差阈值、速度跟踪、是否摔倒）

**本讲不是训练完整策略**。完整的抓取策略或行走策略需要后续课程（强化学习、模仿学习）的方法论支撑。本讲的目标更基础也更关键：**跑通、观察、记录和复盘**——先让任务在仿真里正确地"动起来"，然后理解它为什么这样动。

**本节小结**：机械臂操作和 G1 locomotion 是本讲的两条贯穿线。前者关注末端和物体的交互，后者关注全身姿态和地面接触。两个任务在表面形式上完全不同，但在仿真层面共享同一套拆解框架。本讲的目标不是训练策略，而是建立理解仿真任务的能力。

## **3.3 仿真任务拆解：从真实任务到可运行环境**

两个任务确定后，下一步不是直接打开 MuJoCo 或 Isaac Lab 跑 Demo，而是先回答一个更根本的问题：**"让机械臂抓取杯子"这个真实任务，在仿真环境里需要被拆成哪些组成部分？**

这听起来像是抽象的方法论讨论，但它直接决定了你能否看懂任何一个仿真 Demo 的代码结构。本节提出的"七个问题"是本讲的主框架——后面看到 MuJoCo 的 MJCF 文件、Isaac Lab 的环境配置、G1 的 locomotion 任务时，都回到这七个问题来理解。

### 3.3.1 问题一：任务目标是什么？

任务目标定义了"怎样算成功"。不同的目标导致完全不同的仿真配置：

**机械臂操作的任务目标**：
- Reach：末端执行器到达指定的目标位姿（位置 + 姿态），通常以末端与目标的距离小于某个阈值（如 1 cm）作为成功条件。
- Pick-place：物体从初始位置被抓取并放置到目标位置，通常以物体最终位置与目标位置的距离小于阈值（如 2 cm）作为成功条件。注意，放置后夹爪必须释放物体，否则不算完成。

**G1 locomotion 的任务目标**：
- Standing：保持 base 姿态在指定范围内（如 base 高度不低于初始高度的 80%），持续一段时间。
- Walking：在指定时间内（如 20 秒），base 的实际速度跟踪上指令速度，跟踪误差在一定范围内。
- Turning：类似 walking，但跟踪的是角速度指令。
- Disturbance recovery：在外力作用下不摔倒，恢复到稳定站立。

### 3.3.2 问题二：机器人模型是什么？

机器人模型是仿真任务的核心资产。它不只是 3D 外观，而是包含以下信息的完整描述：

- **运动学结构（Kinematic Tree）**：有哪些 link（连杆），它们之间通过什么类型的 joint（关节）连接？是转动关节（revolute）还是平动关节（prismatic）？关节的父子关系是如何定义的？这决定了机器人的自由度和运动范围。
- **动力学参数**：每个 link 的质量（mass）、质心位置（center of mass）、惯量矩阵（inertia matrix）。这些参数直接影响机器人对外力的响应——质量越大，加速越慢；惯量越大，旋转越难。
- **碰撞几何体（Collision Geometry）**：用于物理碰撞检测的简化几何形状（球、盒子、圆柱或凸包）。注意这不是渲染用的视觉模型——碰撞几何体通常比视觉模型更简化，以降低计算量。
- **执行器（Actuator）**：关节的驱动方式。是位置控制、速度控制还是力矩控制？驱动力上限是多少？这决定了你能对机器人"发什么命令"。
- **传感器（Sensor）**：机器人身上有哪些传感器？关节编码器、IMU、力/力矩传感器、相机？

对于机械臂，模型重点在关节类型、连杆质量和夹爪的碰撞体。对于 G1，模型重点在全身 23+ 个关节的质量分布、足底的接触几何体和 IMU 的姿态感知。

### 3.3.3 问题三：场景和物体是什么？

机器人不是在真空中运动，它需要一个物理上合理的场景：

- **地面/桌面**：是平面还是有纹理？是硬的还是软的？摩擦系数是多少？地面是无限大的，还是有一个边界？
- **操作对象**：对于机械臂，是杯子、方块、还是任意物体？物体的形状、质量、摩擦系数、初始位置是什么？
- **障碍物**：环境中是否有机器人需要避开的物体？
- **光照和视觉**：如果使用视觉传感器，场景需要包含光源和视觉纹理。

在仿真里，这些不是"随便放一放"——每个参数都会影响任务结果。物体的质量决定了抓取时需要的夹持力。桌面的摩擦系数决定了物体是滑过来还是停在原地。

### 3.3.4 问题四：机器人能看到什么？（Observation）

观测（observation）定义了机器人从环境中获取什么信息。这决定了机器人的"感知能力上限"：

**机械臂任务的典型观测**：
- 关节位置（joint positions）：当前每个关节的角度（rad）。
- 关节速度（joint velocities）：当前每个关节的角速度（rad/s）。
- 末端执行器位姿（end-effector pose）：末端在基座坐标系下的 6D 位姿。
- 物体位姿（object pose）：目标物体在基座坐标系下的 6D 位姿（仿真中可直接获取，真机中需要感知系统提供——这就是第 6 讲的核心）。
- 夹爪状态（gripper state）：夹爪的开合程度或夹持力。
- 相机图像（可选）：RGB 图像和深度图（如果任务需要视觉感知）。

**G1 locomotion 的典型观测**：
- 关节位置和速度。
- Base 的线速度和角速度（来自 IMU 或里程计）。
- Base 的姿态（roll、pitch、yaw）。
- 指令（velocity command）：用户给出的目标速度。
- 足底接触力（contact force on each foot）。
- 关节力矩（joint torques）。

值得强调的是：仿真中的观测往往比真机更"完美"——物体位姿可以直接从仿真器中读取真值，不需要经过检测和位姿估计。这既是仿真的优势（可以快速验证任务逻辑），也是 Sim2Real gap 的来源之一（真机上永远没有完美的位姿）。

### 3.3.5 问题五：机器人能输出什么动作？（Action）

动作（action）定义了机器人控制器的输出空间，即"机器人能做什么"：

- **关节位置控制**：直接指定目标关节角度。控制器（通常是 PD 控制器）会根据目标角度和当前角度计算所需的力矩。这是最简单的控制模式，适合位置控制任务。
- **关节速度控制**：指定目标关节角速度。适合需要平滑运动的任务。
- **关节力矩控制**：直接指定关节力矩。最底层、最灵活的控制模式，但也是最难调的——需要处理重力补偿、摩擦补偿等问题。适合强化学习策略直接输出力矩。
- **末端执行器控制**：指定末端执行器的目标位姿（在笛卡尔空间），通过逆运动学（IK）求解关节角度。适合"把末端移到某个位置"这类任务描述。
- **Base velocity command**（G1 特有）：指定目标线速度和角速度，由全身控制器将其转化为关节动作。

动作空间的设计直接影响任务难度和控制精度。事实上，很多仿真任务的"成败"在动作空间设计这一步就已经埋下了伏笔——如果选错了控制模式（例如用一个纯位置控制器去做需要力控的精细操作），后续怎么调参都无法成功。

### 3.3.6 问题六：物理和控制参数是什么？

物理参数定义了仿真世界的"物理规则"。这些参数在真机上是客观存在的物理属性，在仿真里则是可以（也必须）人工设定的数值：

- **接触参数**：接触模型的类型（如 MuJoCo 的 elliptic cone 模型）、接触刚度、接触阻尼、摩擦系数（静摩擦和滑动摩擦）。这些参数直接影响抓取是否稳定、足底是否打滑。
- **质量与惯量**：每个 link 的质量和惯量矩阵。真机的这些参数可以通过 CAD 模型导出，但通常有误差——这是 Sim2Real gap 的重要来源。
- **关节参数**：关节阻尼（joint damping）、关节摩擦（joint friction）、关节限位（joint limits）、执行器力矩上限（actuator force range）。
- **控制参数**：控制频率（control frequency，仿真中通常是 20-1000 Hz）、PD 控制器的比例增益（kp）和微分增益（kd）。
- **积分步长**：物理引擎的积分步长（timestep），通常为 0.001-0.005 秒。步长过大导致数值不稳定，步长过小增加计算量。

这些参数中，摩擦和控制频率对学生来说最容易产生"调一下看看会怎样"的直觉，因此本讲后面的实操部分会重点围绕这两个参数展开。

### 3.3.7 问题七：成功和失败如何判断？

成功判定是仿真任务闭环的最后一步。没有明确的成功/失败判定，仿真只是动画，不是实验。

**机械臂任务**：
- Reach 成功：末端与目标位置的距离 < 阈值（如 1 cm）。
- Pick-place 成功：物体最终位置与目标位置的距离 < 阈值，且物体未被夹爪持握（已释放）。
- 失败条件：超时（如超过 10 秒未完成）、物体掉落、机械臂碰到不可碰撞区域。

**G1 locomotion**：
- Standing 成功：base 高度 > 阈值（如 0.8 倍初始高度），且持续时间达标。
- Walking 成功：实际速度跟踪上指令速度，且 base 姿态保持在安全范围内（未摔倒）。
- 摔倒判定：base 高度低于阈值，或 base 与地面的夹角超过某个角度。

**成功判定不等于 reward**。这是 Isaac Lab 一节的要点之一。Success metric 是"评测时怎样算成功"——它是一个二值化的客观标准。Reward 是"训练时鼓励什么"——它可以是一个连续的函数（如越靠近目标 reward 越大），用来引导策略学习。初学者最容易犯的错误就是把 reward 当作 success metric 来用，或者反过来。

### 3.3.8 全景对照表

| 拆解项 | 机械臂任务 | G1 locomotion |
|---|---|---|
| 任务目标 | reach / pick-place | standing / walking / turning |
| 机器人模型 | 机械臂关节和夹爪 | 全身关节、躯干、足底 |
| 场景物体 | 桌面、目标物 | 地面、扰动 |
| 观测 | 关节、末端、物体 | 姿态、速度、关节、指令 |
| 动作 | 关节或末端控制 | 策略动作或目标关节 |
| 参数 | 摩擦、质量、频率 | 接触、延迟、阻尼 |
| 成功判定 | 误差、抓取、放置 | 不摔倒、速度跟踪 |

**本节小结**：这七个问题——任务目标、机器人模型、场景物体、观测、动作、物理参数、成功判定——构成了理解任何仿真任务的通用框架。学生后面看到任何仿真 Demo，首先应该把这七个问题逐一回答出来。框架本身不是目的，目的是让你在看代码时知道每一行在解决哪个问题。有了这套框架之后，平台选择就不再是"哪个工具更好"的感性判断，而变成了"哪个工具更适合帮我观察哪一类问题"的理性选择。

## **3.4 平台选择：MuJoCo 与 Isaac Lab 分别解决什么问题**

有了仿真任务拆解框架之后，再看平台选择就不会变成工具比较，而是看每个平台最适合帮我们观察哪一类问题。

### 3.4.1 平台选择的原则

初学者面对仿真工具时，最常见的错误是先入为主地追求"更高级"的平台。"Isaac Lab 基于 Isaac Sim，肯定比 MuJoCo 好"——这种想法忽略了工具和任务之间的匹配关系。

正确的选择逻辑是：
1. **先明确你要观察什么**：是模型和物理参数的即时反馈？还是强化学习的大规模并行评测？还是视觉传感器的渲染质量？
2. **再选最匹配的工具**：轻量任务用轻工具，复杂任务用重工具。
3. **入门阶段先看清结构，再看规模**：先看懂一个任务怎么在仿真里跑起来，再考虑并行和加速。

本讲使用两个平台，不是因为"一个不够用"，而是为了让学生看到两种不同层次的仿真问题：**MuJoCo 让你看到任务的骨架（模型、关节、碰撞、物理参数）**，**Isaac Lab 让你看到任务的神经系统（observation、action、reward、并行评测）**。

### 3.4.2 MuJoCo：轻量物理引擎，看清任务骨架

MuJoCo（Multi-Joint dynamics with Contact）是一个专注于多关节动力学和接触物理的仿真引擎。它由 DeepMind 收购并开源，是当前机器人学和强化学习研究中最广泛使用的物理引擎之一。

**MuJoCo 的核心特点**：

1. **轻量且高效**：MuJoCo 的代码库紧凑（核心引擎用 C 编写），安装和启动都非常快。不需要 GPU 加速也能流畅运行大多数机械臂和简单运动任务。对于想在笔记本上快速验证想法的学生来说，这是巨大的优势。

2. **模型文件直观（MJCF / XML）**：MuJoCo 使用 MJCF（MuJoCo XML Format）来描述机器人模型和场景。一个 MJCF 文件打开后，可以清晰地看到：
   - `<body>` — 机器人的各个连杆
   - `<joint>` — 关节的类型、范围、阻尼
   - `<geom>` — 碰撞几何体的大小、摩擦系数
   - `<site>` — 预定义的参考点（如末端执行器位置）
   - `<actuator>` — 执行器类型和控制参数

   这种结构化的文本格式，让初学者可以直接通过阅读文件来理解一个机器人是如何在仿真中被"组装"起来的。

3. **物理参数直接可见和可调**：MuJoCo 中，摩擦系数、质量、惯量、阻尼、接触刚度等参数都在模型文件中显式声明，修改后重新加载即可看到效果。这种"改一个参数 → 看一个效果"的即时反馈，对于建立物理直觉来说是无可替代的。

4. **适合控制和小规模 RL**：MuJoCo 的 Python 绑定提供了灵活的 step-by-step 控制接口，可以方便地接入各种控制器（PID、MPC、RL policy）。

**MuJoCo 在本讲中的角色**：负责帮学生理解仿真任务的骨架——看懂 MJCF 模型文件、理解关节和碰撞体的含义、通过修改物理参数观察任务行为变化。本讲中 MuJoCo 承载的是机械臂 reach 和 pick-place 的实操。

### 3.4.3 Isaac Lab：机器人学习框架，看清环境组织

Isaac Lab 是 NVIDIA 基于 Isaac Sim 构建的机器人学习框架。它在 Isaac Sim 的强大渲染和物理仿真能力之上，提供了统一的环境接口和并行训练能力。

**Isaac Lab 的核心特点**：

1. **统一的机器人学习环境接口**：Isaac Lab 提供了标准化的 environment 接口，任何任务都需要定义 observation space、action space、reward function、termination condition 和 success metric。这种统一性让不同任务之间的比较和迁移变得可能。

2. **GPU 并行仿真**：Isaac Lab 可以在单个 GPU 上同时运行数千个仿真环境。每个环境有不同的初始状态（物体位置随机化、关节初始角度随机化），从而实现大规模并行数据采集。对于强化学习来说，这直接意味着"样本效率"——原来需要几天的训练，现在可能几小时就能完成。

3. **丰富的传感器支持**：基于 Isaac Sim 的渲染能力，Isaac Lab 支持相机（RGB、深度、语义分割）、LiDAR、IMU 等多种传感器的仿真。这对后续的感知课程来说是重要的基础。

4. **适合复杂机器人和大规模评测**：人形机器人、四足机器人的 locomotion 任务，以及需要大量随机化评测的操作任务，在 Isaac Lab 中都比在轻量引擎中更自然。

**Isaac Lab 在本讲中的角色**：负责帮学生理解机器人学习环境的组织结构——observation、action、reward、done、success metric 各自是什么、如何协同工作，以及多环境并行评测的意义。本讲中 Isaac Lab 承载的是机械臂任务和 G1 locomotion 的实操。

### 3.4.4 MuJoCo 与 Isaac Lab 对比：什么时候用哪个

**什么时候优先用 MuJoCo**：
- 想快速理解一个机器人模型的运动学和动力学结构。
- 想调试单个物理参数（摩擦、质量、阻尼）对任务的影响。
- 做控制算法的原型验证。
- 计算资源有限，在笔记本上工作。
- 任务是机械臂操作、灵巧手控制等关节数较少（< 30 DoF）的场景。

**什么时候优先用 Isaac Lab**：
- 需要大规模的并行数据采集（数千个环境同时运行）。
- 需要高质量的传感器仿真（相机、LiDAR）。
- 任务是复杂人形机器人的 locomotion 或全身操作。
- 需要用标准化的 RL 训练接口（与 RLlib、skrl 等库集成）。
- 任务需要大量 domain randomization 来提升 Sim2Real 迁移能力。

| 对比维度 | MuJoCo | Isaac Lab | 本讲中的作用 |
|---|---|---|---|
| 上手门槛 | 相对轻量 | 环境更重 | 先用 MuJoCo 建立直觉 |
| 运行成本 | 较低 | 更依赖 GPU 和 Isaac Sim | Isaac Lab 用于并行和复杂任务 |
| 模型理解 | MJCF / XML 结构清楚 | asset、articulation、scene 更工程化 | MuJoCo 看模型骨架，Isaac Lab 看环境组织 |
| 物理与接触 | 适合快速调试摩擦、质量、碰撞 | 适合复杂场景和大规模评测 | 两者都可用于 Sim2Real 讨论 |
| 传感器支持 | 可用但不是本讲重点 | 更适合复杂传感器和渲染 | 为后续感知课程埋线索 |
| 并行仿真 | 不是本讲重点 | 核心优势之一 | Isaac Lab 用于成功率和 RL 评测 |
| 适合任务 | 机械臂、灵巧手、控制验证 | 人形、四足、大规模 RL | 本讲分别对应机械臂线和 G1 线 |

**本节小结**：平台选择要服务任务，不要先入为主追求"更高级"的工具。MuJoCo 适合帮助学生理解仿真任务的骨架——模型、关节、碰撞、物理参数、控制接口。Isaac Lab 适合帮助学生理解机器人学习环境——observation、action、reward、done、success metric、多环境并行。本讲先用 MuJoCo 建立直觉，再用 Isaac Lab 扩展到机器人学习和人形机器人任务。

## **3.5 仿真生态还有哪些平台**

### 本节定位

平台讨论至此，学生自然会问："除了 MuJoCo 和 Isaac Lab，还有没有别的选择？"本节给出简要的全景图，但不做详细对比。核心原则不变：**平台多不等于都要学，任务驱动工具选择**。

### 按用途分类

**通用物理仿真/研究向**：
- **PyBullet**：轻量、Python 友好，RL 社区常用。基于 Bullet 物理引擎，提供了类似 Gym 的接口。适合快速原型和小规模 RL 实验。
- **CoppeliaSim**（原 V-REP）：功能全面，支持多物理引擎后端、多编程接口（Python、C++、MATLAB、ROS）。工业和教育场景都有应用。
- **Drake**：MIT / Toyota Research Institute 开发的控制理论导向仿真器。擅长多体动力学和最优化控制。如果你的任务涉及复杂的约束优化和控制理论，Drake 是值得关注的选择。
- **Chrono**：多体动力学引擎，擅长颗粒物料、柔性体、车辆动力学等复杂物理场景。适合挖掘、建筑、农业机器人等特殊领域。

**ROS 生态经典**：
- **Gazebo / Ignition**：ROS 生态的标准仿真器，与 ROS/ROS2 深度集成。如果你已经在用 ROS，Gazebo 几乎是默认选择。Ignition（新版 Gazebo）在渲染和性能上有大幅改进。

**教学/入门友好**：
- **Webots**：界面友好，商业与开源双版本，适合教学和快速上手。提供了大量预置的机器人模型和场景。

**GPU 并行/下一代**：
- **Genesis**：超高速并行仿真引擎，核心用 Python 编写，支持 GPU 加速。2024 年底开源后迅速获得关注。特点是仿真速度极快（可达 4300 万 FPS），支持可微分物理和生成式能力。适合需要海量数据生成和快速迭代的场景。
- **Newton**：NVIDIA 基于 Warp（GPU 加速的 Python 库）构建的下一代可微分物理引擎。与 Isaac Sim 生态互补，适合需要可微分物理的场景。
- **Brax**（及其他 JAX 系）：基于 JAX 的物理仿真引擎，运行在 GPU/TPU 上，支持大规模并行和自动微分。RL 研究社区常用。

**特定领域**：
- **CARLA**：自动驾驶仿真，支持多种传感器、交通场景和天气条件。
- **AirSim**：微软开发的无人机和自动驾驶仿真器，基于 Unreal Engine。
- **SAPIEN / ManiSkill**：专注于物体操作任务（铰接物体、工具使用），提供标准化的操作任务 benchmark。ManiSkill 特别适合需要大量交互式操作数据的研究。
- **robosuite**：基于 MuJoCo 的机械臂操作仿真框架，提供了标准化的机械臂任务和控制器接口。

**游戏引擎衍生**：
- **Unity + ML-Agents**：利用 Unity 的渲染能力进行逼真场景仿真，适合需要高质量视觉感知的任务。
- **Unreal Engine**：通过 AirSim 等插件提供高保真感知仿真。

### 一句话选型收尾

> 轻量学控制 → MuJoCo / PyBullet；大规模并行训练 → Isaac Lab / Genesis / Brax；真实感知仿真 → Unreal / CARLA / AirSim；ROS 集成 → Gazebo。

**本节小结**：本节是拓展阅读内容。仿真平台生态丰富，但没有一个平台适合所有任务。选型时回到 3.4 节的原则——先明确要观察什么，再选最匹配的工具。对初学者来说，用 MuJoCo 建立物理直觉、用 Isaac Lab 理解 RL 环境接口，是最有效的入门路径。

## **3.6 MuJoCo 线：用机械臂 reach / pick-place 看懂模型、控制和物理参数**

平台分工清楚后，先从 MuJoCo 开始，用一个最小机械臂任务把模型、控制和物理参数看清楚。

### 3.6.1 为什么先用 MuJoCo

MuJoCo 处理机械臂操作任务有三重优势：

第一，**轻量**。不需要 GPU、不需要复杂的依赖管理、不需要等几分钟的启动时间。打开终端，`pip install mujoco`，几分钟后就能跑起来。

第二，**模型文件直观**。一个机械臂的完整描述在一个 MJCF/XML 文件中，打开就能看到所有结构。这不像 Isaac Lab 中模型被包装在 USD 文件和 articulation 配置里，中间经过了多层抽象。

第三，**参数修改即时生效**。改一个摩擦系数，保存文件，重新加载——几秒钟就能看到效果。这种即时反馈对于初学者建立"参数 → 行为"的因果关系理解至关重要。

### 3.6.2 先看懂 MJCF 模型文件

在跑任何 Demo 之前，我们先花时间读一个最小化的 MJCF 文件。这是 MuJoCo 学习中最容易被跳过、但实际上最重要的一步。不读模型文件就去跑 Demo，就像不开机盖就去修车——出了问题完全不知道从哪里查。

MJCF 文件是一个结构化的 XML 文档，包含以下核心标签：

**`<mujoco>`**：根标签，整个模型的容器。

**`<worldbody>`**：世界坐标系下的所有物体。包括地面、机器人、操作对象等。地面上通常用一个 `<geom>` 标签表示——一个尺寸很大的盒子，type 为 "plane"。

**`<body>`**：一个刚体连杆。每个 body 有其名称、位置（`pos`）、朝向（通过 `quat`、`euler` 或 `axisangle` 指定）。body 可以嵌套——子 body 的位置是相对于父 body 的坐标系定义的。这种嵌套关系构成了机器人的运动学树。例如：

```xml
<body name="base_link" pos="0 0 0">
  <body name="shoulder" pos="0 0 0.3">
    <body name="upper_arm" pos="0 0.1 0">
      <!-- 前臂是上臂的子 body -->
      <body name="forearm" pos="0 0 0.25">
        <!-- 手腕是前臂的子 body -->
        <body name="wrist" pos="0 0 0.2">
        </body>
      </body>
    </body>
  </body>
</body>
```

**`<joint>`**：定义父子 body 之间的连接方式。最关键的两个参数是 `type`（关节类型）和 `range`（运动范围）：
- `type="hinge"`：转动关节（1 个自由度），如人的肘关节。
- `type="slide"`：平动关节（1 个自由度），如抽屉。
- `type="ball"`：球关节（3 个自由度），如人的肩关节。
- `type="free"`：自由关节（6 个自由度），通常只给 base 或自由物体用。

```xml
<joint name="shoulder_pitch" type="hinge" axis="0 1 0" range="-1.57 1.57"/>
```

`axis` 指定了关节旋转轴，`range` 指定了最小和最大角度（弧度）。

**`<geom>`**：几何体。这是碰撞检测和可视化的基本单位：
- `type`：形状类型（box、sphere、cylinder、capsule、mesh）。
- `size`：几何体尺寸，不同类型含义不同。对于 box，是半边长（half-size）；对于 sphere，是半径。
- `mass`：质量（kg）。如果未指定，MuJoCo 会根据几何体体积和默认密度自动计算。
- `friction`：摩擦系数。可以是一个标量（三个方向相同），也可以是三个值（滑动摩擦、扭转摩擦、滚动摩擦）。
- `rgba`：颜色和不透明度（RGBA）。

```xml
<geom name="link_geom" type="cylinder" size="0.05 0.15" mass="0.5"
      friction="0.7 0.005 0.0001" rgba="0.8 0.2 0.2 1"/>
```

**`<site>`**：预定义的参考点。它不参与物理计算，但提供了一个方便的位置/朝向引用。最常见的用法是定义末端执行器的参考点：

```xml
<site name="end_effector" pos="0 0 0.1" size="0.01"/>
```

代码中可以通过 `data.site('end_effector')` 获取这个位置的当前坐标。

**`<actuator>`**：执行器定义。最常见的是 `<motor>`，它为关节提供驱动力：

```xml
<actuator>
  <motor name="shoulder_motor" joint="shoulder_pitch" gear="1" ctrlrange="-50 50"/>
</actuator>
```

`joint` 指定驱动的关节，`gear` 是传动比，`ctrlrange` 是控制输入的范围（力矩上限）。

### 3.6.3 跑 reach：从目标点到末端轨迹

有了模型文件的理解基础，我们来完成第一个 MuJoCo 任务：让机械臂末端到达指定的目标点。

**最小 reach 脚本的结构**：

```python
import mujoco
import mujoco.viewer
import numpy as np

# 1. 加载模型
model = mujoco.MjModel.from_xml_path('robot_arm.xml')
data = mujoco.MjData(model)

# 2. 定义目标点（世界坐标系下）
target_pos = np.array([0.3, 0.0, 0.2])

# 3. 控制循环
with mujoco.viewer.launch_passive(model, data) as viewer:
    for step in range(1000):
        # 获取当前末端位置
        ee_pos = data.site('end_effector').xpos.copy()

        # 计算误差
        error = target_pos - ee_pos

        # 简单的比例控制器（通过 Jacobian 计算关节增量）
        # 实际代码见配套仓库
        Kp = 2.0  # 比例增益
        # ... Jacobian-based IK ...

        # 步进仿真
        mujoco.mj_step(model, data)

        # 检查是否到达
        dist = np.linalg.norm(error)
        if dist < 0.01:
            print(f"Reached target in {step} steps, final error: {dist:.4f} m")
            break
```

在 reach 实验中，学生应重点观察：
1. **末端轨迹**：是否平滑？有无抖动？可以用 viewer 直接观察，也可以记录 data.site('end_effector').xpos 的历史值来绘制 3D 轨迹。
2. **收敛速度**：到达目标需要多少步？这和控制器增益（Kp）直接相关——Kp 太大会过冲和振荡，Kp 太小则收敛太慢。
3. **稳态误差**：最终停在离目标多远的位置？这和控制器类型（P/PI/PID）以及关节阻尼有关。

### 3.6.4 跑 pick-place：加入物体接触

reach 只涉及机械臂自身的运动，pick-place 在此基础上增加了**物体接触**——这是仿真中最难预测的部分。

**物体是独立 body**：在 MJCF 中，被抓取的物体是一个独立的 `<body>`，有它自己的质量和碰撞几何体。初始时它被放在桌面上，通过重力保持静止。

```xml
<body name="object" pos="0.3 0.0 0.05">
  <freejoint/>  <!-- 物体可以自由移动 -->
  <geom name="object_geom" type="box" size="0.03 0.03 0.03"
        mass="0.1" friction="0.5 0.005 0.0001"/>
</body>
```

**抓取判断**：夹爪闭合后，物体是否被抓起来取决于接触力。在 MuJoCo 中，可以通过检查夹爪左右两侧与物体之间的接触次数和接触力来判断：

```python
# 检查夹爪与物体的接触
n_con = 0
for i in range(data.ncon):
    contact = data.contact[i]
    geom1 = model.geom(contact.geom1).name
    geom2 = model.geom(contact.geom2).name
    if ('object' in geom1 or 'object' in geom2) and \
       ('gripper' in geom1 or 'gripper' in geom2):
        n_con += 1

is_grasped = n_con >= 2  # 至少左右两个夹指都接触
```

**为什么 pick-place 比 reach 更容易失败**：

1. **接触不充分**：如果夹爪闭合位置离物体太远（哪怕只有几毫米），夹指碰不到物体——抓取直接失败。
2. **滑脱**：如果摩擦系数不够，或者夹持力太小，物体在抬升过程中会从夹爪中滑出。
3. **碰撞排斥**：如果夹爪闭合速度太快，碰撞力可能把物体推走而不是握住。
4. **放置不稳定**：放置时，如果物体底部的摩擦系数太小或者放置速度太快，物体可能滚动或滑出目标区域。

### 3.6.5 改参数、看变化

MuJoCo 最大的教学优势在这一步显现：改一个参数，几秒后就能看到任务行为的变化。以下是建议的实验序列：

**实验 1：改变目标点位置**
- 将目标点从 (0.3, 0, 0.2) 移到 (0.3, 0.2, 0.05)。
- 观察：机械臂是否能够到达？如果到达了，轨迹和之前有什么不同？如果到达不了（超出工作空间），IK 求解器是报错还是返回一个最近的可达解？

**实验 2：改变物体质量**
- 将物体的 `mass` 从 0.1 kg 改为 0.5 kg。
- 观察：同样的夹持力还够不够？抬升过程中夹爪是否会滑脱？需要增加多少夹持力才能稳定抓取？

**实验 3：改变摩擦系数**
- 将桌面的 `friction` 从默认值改为 0.1（非常光滑）。
- 观察：物体在桌面上是否更容易滑动？夹爪接触物体时，物体是固定不动还是被推开？

**实验 4：改变控制频率**
- 将控制循环的频率从 100 Hz 降到 20 Hz。
- 观察：轨迹是否变得更粗糙？末端是否出现超调？稳态误差是否变大？

每个实验的结果都应记录在统一的实验记录表中（见 3.10 节）。关键不是"调出一个好的参数"，而是**把参数和现象的因果关系说清楚**——"我做了什么改动，观察到了什么变化，我认为原因是什么"。

**本节小结**：MuJoCo 不只让你"看机器人动"，更重要的是让你看懂任务的结构。通过阅读 MJCF 文件理解机器人的运动学和动力学组成，通过跑 reach 和 pick-place 理解控制和接触，通过改参数建立物理直觉。MuJoCo 让我们在最小复杂度下看清了任务的骨架。下一步，Isaac Lab 将帮我们理解机器人学习环境如何围绕 observation、action、reward 组织起来。

## **3.7 Isaac Lab 线：用机械臂任务看懂环境接口与并行评测**

MuJoCo 帮我们理解了单个任务如何动起来。但机器人学习需要的不只是"一个能跑的任务"——它需要标准化的环境接口、批量并行评测、以及为强化学习准备的 Reward 体系。Isaac Lab 在这一层上给出了答案。

### 3.7.1 从 MuJoCo 到 Isaac Lab：关注层次的变化

在 MuJoCo 中，我们直接操作仿真器的底层接口：`data.ctrl`、`mujoco.mj_step`、`data.site().xpos`。每一步都要手动管理。

在 Isaac Lab 中，这些底层细节被封装在一层标准化的环境接口之后。你面对的不再是"仿真器的 step 函数"，而是一个符合强化学习约定的 **Environment** 对象。这种封装不是简单的语法糖——它解决了一个关键问题：**让你的任务可以被任何 RL 算法调用，也可以让任何 RL 算法评价你的任务**。

### 3.7.2 Isaac Lab 的任务组成

一个 Isaac Lab 任务由以下层级组成：

| 层级 | 说明 | 对应概念 |
|---|---|---|
| **Scene** | 包含所有 asset 和 articulation 的物理场景 | MuJoCo 的 worldbody |
| **Asset** | 机器人、物体的 USD 或 URDF 模型 | MuJoCo 的 body/geom |
| **Articulation** | 有运动学结构的机器人模型 | MuJoCo 的 body+joint 树 |
| **Sensor** | 相机、IMU、接触传感器等 | MuJoCo 的 sensor/site |
| **Environment** | 将上述组合为 RL 接口 | MuJoCo 的 step 循环 |

Isaac Lab 对 asset 的管理比 MuJoCo 更工程化。机械臂模型通常以 URDF 或 USD 格式加载，通过 `ArticulationCfg` 配置其初始状态、关节属性和物理参数。场景中的物体（如桌面、目标物）通过 `RigidObjectCfg` 配置。

### 3.7.3 五个核心接口

在 Isaac Lab 中，任何任务都需要实现以下五个接口。它们构成了机器人学习环境的"协议层"：

**（1）Observation（观测空间）**

Observation 定义了策略（policy）在每个时间步可以获取的信息。Isaac Lab 中的观测分为两类：
- **Policy observation**：策略真正使用的观测，可以是关节状态、末端位姿、物体位姿等的拼接向量。
- **Critic observation**（可选）：价值函数（critic）使用的观测，可能包含额外的特权信息（如物体的精确位姿、接触力真值），这些信息在仿真中可获得但在真机中不可得。

需要强调的是：**观测空间的设计直接影响策略学习的难度**。如果观测中缺少关键信息（例如没有物体位置），策略永远无法学会抓取。如果观测中包含无关信息（噪声过大），策略需要更多的样本来学会忽略它。

Isaac Lab 中使用 `ObservationCfg` 来配置观测策略，例如：
- `"joint_pos"`：关节位置
- `"joint_vel"`：关节速度
- `"ee_pos"`：末端执行器位置
- `"object_pos"`：物体位置

**（2）Action（动作空间）**

Action 定义了策略的输出。在 Isaac Lab 中，action 通常是关节位置目标或关节力矩目标，维度等于被控关节的数量。

Isaac Lab 支持多种 action 解析方式：
- **Joint position**：策略输出目标关节位置，底层 PD 控制器计算力矩。
- **Joint effort**：策略直接输出力矩，通过 `actuator_group` 直接施加到关节。
- **Delta joint position**：策略输出相对于当前关节位置的增量。

机械臂任务的 action space 通常是 6-7 维（6 个关节位置 + 1 个夹爪开合），取值范围经过归一化（如 [-1, 1]），再由环境内部的缩放参数映射到实际关节角度或力矩范围。

**（3）Reward（奖励函数）**

Reward 是 Isaac Lab 区别于 MuJoCo 的一个核心概念。MuJoCo 中你手动判断"到了/没到"，Isaac Lab 中你需要设计一个**连续的 reward 函数**来告诉策略"你离目标有多近"。

机械臂 reach 任务的典型 reward 设计：

```python
# 距离奖励：末端越接近目标，reward 越大（负值，所以越大 = 越近）
dist_reward = -torch.norm(ee_pos - target_pos, dim=-1)

# 接近奖励（可选）：如果末端比上一步更接近目标，给正向奖励
approach_reward = prev_dist - curr_dist

# 成功奖励（可选）：到达目标时给予一次性奖励
success_reward = (curr_dist < 0.01).float() * 10.0

# 总 reward
reward = dist_reward + 0.5 * approach_reward + success_reward
```

Reward 设计有几个常见的坑：
- **量级不匹配**：如果 distance reward 的量级是 -0.1 到 0，而 success reward 是 100，策略可能只学会"随便动一动碰运气"而不是"稳定地向目标移动"。
- **稀疏 vs 稠密**：如果只有 success reward（到达才给分），对于初学者来说可能永远找不到正确的方向——这就是所谓的"稀疏奖励"问题。
- **reward 和 success metric 混淆**：Reward 可以给 0.5 分（部分接近），success metric 只能是 0 或 1。

**（4）Done（终止条件）**

Done（或 termination）定义了"何时停止当前 episode"。一个 episode 可以在以下情况下终止：
- **成功**：任务目标达成（末端到达目标）。
- **失败**：任务进入不可恢复的状态（物体掉落、关节超限）。
- **超时**：达到最大 episode 长度（如 500 步）。

Isaac Lab 中，`terminated`（因失败结束）和 `truncated`（因超时结束）是两个不同的标志。这种区分对 RL 训练很重要：
- Terminated 的 episode 意味着策略做了"坏"的事，Critic 应该学到这是一个低价值状态。
- Truncated 的 episode 只是时间到了，不代表当前状态本身的好坏。

**（5）Success Metric（成功判定）**

Success metric 是评测时使用的二值化标准。它和 reward 的区别：

| | Reward | Success Metric |
|---|---|---|
| 输出 | 连续浮点数，可正可负 | 二值 (0/1) |
| 用途 | 训练时引导策略学习 | 评测时统计成功率 |
| 频率 | 每步计算 | Episode 结束时判定 |
| 设计原则 | 稠密、有梯度 | 精确、无歧义 |

例如，reach 任务的 reward 每步都给（基于距离），但 success 只在 episode 结束时判定："末端到目标的距离 < 1 cm？是/否"。

**本节小结**：Isaac Lab 的五个核心接口——observation、action、reward、done、success metric——构成了机器人学习环境的标准协议。理解这些接口不是为了记住 Isaac Lab 的 API，而是为了理解机器人学习环境的组织逻辑：策略看到什么？策略输出什么？训练时鼓励什么？何时停止？评测时怎样算成功？这五个问题，是 MuJoCo 的底层 step 循环之上、RL 训练之下的一层关键抽象。

### 3.7.4 多环境并行：一次评测数百种初始状态

Isaac Lab 的一项核心能力是**多环境并行**。它利用 GPU 并行启动数百甚至数千个仿真环境，每个环境的初始状态不同——物体位置有微小偏移、关节初始角度随机化、摩擦系数有差异。

**为什么需要并行？**

在单环境评测中，你只能看一个特定初始条件下的成功率。如果机械臂在这个条件下成功了，你无法知道它在"物体往左偏 2 cm"的条件下是否也能成功。逐一测试几百种初始条件太慢——每个条件都需要几秒钟的仿真时间，几百个就是十几分钟。

多环境并行的价值：几百个环境同时跑，每个有不同的初始条件，每步仿真同时推进。你在几十秒内就能得到几百个条件下的成功率统计。

这对强化学习的意义更深远：并行环境意味着**一个 step 就能收集几百条 transition**，而不是一条。对于需要数百万条 transition 的 RL 训练来说，这直接将训练时间从"几天"压缩到"几小时"。

**并行环境的核心机制**：
1. 在 GPU 上创建 N 个环境副本，每个有独立的物理状态。
2. 每个 step，控制器同时为所有环境计算 action。
3. 物理引擎同时推进所有环境的仿真。
4. 收集所有环境的 (obs, action, reward, next_obs, done) 作为一批数据。
5. 将这些数据送入 RL 算法进行训练。

**本节小结**：多环境并行不是简单的"跑快一点"，而是从根本上改变了评测和训练的数据规模。单环境 = 串行采样，多环境并行 = 批量采样。对于研究来说，多环境并行让"系统性评测"（而不是"跑通一次就完事"）成为可能。

## **3.8 G1 locomotion 线：用人形机器人任务理解运动仿真**

机械臂任务关注末端和物体，人形机器人任务关注的是全身平衡和速度指令。从机械臂到 G1，不只是换了机器人模型，而是换了一套认知框架。

### 3.8.1 运动任务的本质差异

操作任务的核心问题是：**"末端到哪里？物体抓没抓住？"** 这是一个以目标物体为中心的坐标系。

运动任务的核心问题是：**"全身是否稳定？速度是否跟上？"** 这是一个以机器人的 base（躯干）为参考、以地面接触为约束的系统性问题。

具体来说，两者有五个本质差异：

| 维度 | 机械臂操作 | G1 Locomotion |
|---|---|---|
| 关注点 | 末端 + 物体 | Base 姿态 + 全身平衡 |
| 接触方式 | 夹爪与物体的主动接触 | 足底与地面的持续接触 |
| 自由度数量 | 6-7 DoF | 23+ DoF（全身关节） |
| 欠驱动程度 | 完全驱动（每个关节都有执行器） | 欠驱动（base 的 6 个 DoF 没有直接执行器，通过腿关节间接控制） |
| 失败模式 | 抓空、滑脱、碰撞 | 摔倒、失稳、速度跟踪失败 |
| 成功判定 | 末端误差、物体位置 | 不摔倒 + 速度跟踪 + 能耗合理 |

理解这些差异之后，再看 locomotion 任务的各个子任务，就不会把它当作"另一个 Demo"，而是会关注 locomotion 特有的观测、动作和判定逻辑。

### 3.8.2 Standing：站着不动比走着更难

**站着不动不是"什么都不做"**。要让 G1 稳定站立，全身的关节需要持续微调来对抗重力。如果完全不做控制，重力会让机器人直接倒下。

Standing 任务的核心考核点：
- **静态稳定性**：base 的姿态（主要是 roll 和 pitch）是否保持在安全范围内？如果在站立时 base 有持续的、不可衰减的振荡（例如 roll 角来回摆动 ±5 度），说明控制器的刚度或阻尼设置不当。
- **足底接触**：双脚是否均匀受力？如果一只脚的接触力显著小于另一只脚，说明重心偏移过多，长时间可能导致机械疲劳或倾覆。
- **关节抖振**：高频低幅的关节振荡（chattering）是仿真中常见的问题，通常源于接触刚度过高、时间步长过大或控制器增益不匹配。

**观察要点**：
1. 记录 base 的 roll、pitch 角随时间的变化。正常站立下，这两个角度应在 ±1 度以内。
2. 记录左右脚的接触力。如果差值超过 20%，检查机器人模型的重心定义和关节初始角度。
3. 如果出现高频抖动，尝试调低 PD 控制器的 Kp 或增大关节阻尼。

### 3.8.3 Walking：速度指令怎么变成步态

Walking 是 locomotion 任务的核心。它的输入是一个速度指令（base velocity command）——例如"以 0.3 m/s 的速度向前走"，输出是全身 23+ 个关节的协调动作。

**Base velocity command 的含义**：
- 线性速度指令（vx, vy）：期望 base 在 x（前后）和 y（左右）方向上的移动速度（m/s）。
- 角速度指令（ωz）：期望 base 绕 z 轴（垂直轴）的旋转速度（rad/s）。
- 这三种速度指令可以任意组合——例如同时向前走和向右转。

需要理解的关键概念：**base velocity command 是用户的意图，不等于机器人一定做得到**。如果命令机器人以 2 m/s 的速度前进，而它的物理极限是 1 m/s，它要么走不到这个速度（速度跟踪误差很大），要么因为强行加速而摔倒。

**Walking 的观测要点**：
1. **速度跟踪误差**：指令速度 vs 实际 base 速度。好的 walking 控制器应该让跟踪误差在 10-20% 以内。
2. **步态周期**：迈步的频率、步幅是否稳定？如果步态从规则的交替步变成了不规则的急促步，说明控制器接近失稳。
3. **足底接触序列**：正常的行走中，足底接触是规律的交替模式——左脚离地 → 左脚落地 → 右脚离地 → 右脚落地。如果这个序列变得混乱（如双脚同时离地很长时间），说明可能有跳跃或异常步态。
4. **Base 高度变化**：行走中 base 应有轻微的高度波动（几厘米），但如果 base 高度大幅下降（如 10 cm 以上），可能是膝或髋关节过度弯曲，接近蹲伏甚至摔倒。

### 3.8.4 Turning：转向的平衡挑战

Turning（转向）在 walking 的角速度指令基础上增加了平衡挑战：机器人需要在保持前进速度的同时，绕垂直轴旋转。

转向时的不对称性：内侧脚（靠近旋转中心）和外侧脚（远离旋转中心）的步幅、受力有很大差异。内侧脚的步幅更小，外侧脚的步幅更大。如果这种差异处理不好，机器人可能：
- 内侧脚"绊"到外侧脚（自碰撞）。
- 外侧脚过度伸展导致踝关节超限。
- 身体向外侧倾斜导致失稳。

**观察重点**：对比线速度指令 (0.3, 0, 0) + 角速度指令 0 rad/s（纯前进）和 (0.3, 0, 0) + 角速度指令 0.5 rad/s（前进 + 右转）下的 base 轨迹和关节动作。正常转向中，base 的轨迹应是一个平滑的弧线，而不是突然的折线。

### 3.8.5 Disturbance Recovery：看推送后怎么恢复

Disturbance recovery 是运动仿真的"压力测试"。在机器人站立或行走时，施加一个外部推力（模拟被推了一下），观察它是否能恢复平衡。

扰动的方式：
- **力脉冲**：对 base 施加一个短时间的力（如 50 N，持续 0.1 秒）。
- **位移扰动**：瞬间改变 base 的位置或姿态。

**恢复策略的观察分级**：
1. **踝关节补偿**（最优）：通过踝关节的微调来对抗小扰动，base 几乎不移动。这是最节能的恢复方式，适用于小扰动。
2. **迈步恢复**：扰动较大的情况下，机器人被迫迈出一步来建立新的支撑面。如果迈步及时、步幅合适，可以避免摔倒。
3. **摔倒**（最差）：无法通过任何策略恢复，base 高度低于阈值或 base 与地面夹角过大。

**观察重点**：
- 需要多大的力才能让机器人摔倒？这个阈值反映了控制器的鲁棒性。
- 摔倒前是哪个部位先失稳？是踝关节角度过大？还是膝关节弯曲过度？还是躯干倾斜？
- 恢复是否过度？好的恢复应该让机器人回到原来的状态，而不是大幅度地朝反方向摆动（overshoot）。

### 3.8.6 摔倒分析的框架

摔倒不是"Demo 失败"这么简单。一次摔倒背后可能有多种原因：

1. **指令过大**：用户给的速度指令超出了机器人当前的物理能力。
2. **接触问题**：足底摩擦系数过低导致打滑，或接触刚度过低导致足底"穿透"地面。
3. **动作异常**：控制器输出了不合理的关节动作（如踝关节突然大幅翻转）。
4. **参数问题**：关节阻尼过大导致响应迟缓，或质量/惯量设置与实际模型不匹配。

学生应能根据观察数据（base 姿态、速度跟踪、足底接触力、关节角度）对每一起摔倒进行上述四个方向的原因分析，而不是停留在"它摔了"的浅层描述。

**本节小结**：G1 locomotion 关注的是全身姿态、速度跟踪和平衡。与机械臂任务的"末端导向"不同，locomotion 是一个系统性问题——base 的运动受限于双腿和地面的接触约束。Standing 挑战静态稳定性，Walking 挑战指令跟踪与步态协调，Turning 挑战不对称运动的平衡，Disturbance recovery 挑战极端条件下的鲁棒性。摔倒本身不是失败——看不懂为什么摔才是。

## **3.9 Sim2Real 线：为什么仿真成功不等于真机成功**

三条仿真线都跑通后，需要回到真实世界：这些仿真结果为什么不一定能直接迁移到真机？如果仿真里一切完美，真机上却频频失败，那仿真的价值在哪里？

### 3.9.1 直观现象：仿真的"完美世界"和真机的"粗糙现实"

先看几个典型例子，它们代表了 Sim2Real gap 最常见的表现：

**例子 1：仿真里能抓住，真机里物体滑掉**。仿真中的接触模型假设夹爪和物体之间是理想的库仑摩擦——摩擦系数恒定、接触面完全平整。真机上，物体的表面可能有油污、灰尘或微小的不平整，夹爪的橡胶垫可能已经磨损。这些微观差异导致了宏观上的抓取失败。

**例子 2：仿真里轨迹平滑，真机里抖动明显**。仿真中的电机是理想的——力矩输出瞬间响应，没有齿隙（backlash），没有弹性变形。真机上的电机有响应延迟、传动间隙、连杆弹性，这些因素叠加起来导致末端轨迹出现高频抖动或位置过冲。

**例子 3：仿真里 G1 能走，真实地面上打滑或失衡**。仿真中的地面是完美平面，摩擦系数均匀。真实地面上，地毯和瓷砖的摩擦系数完全不同，地面上可能有细微的坡度、缝隙或异物。足底的橡胶在不同的温湿度下性能也不同。

这三个例子说明了一个核心事实：**仿真不是真机的"低精度版本"，而是真机的"理想化版本"**。两者之间的差距不在精度高低，而在于仿真忽略了许多真机中不可避免的不确定性。

### 3.9.2 Sim2Real gap 的六个源头

将上述现象系统化，Sim2Real gap 主要来自以下六个方面：

**（1）接触模型差异**

仿真引擎的接触模型是真实物理的简化近似。MuJoCo 使用的接触模型（如 elliptic cone 或 pyramidal cone）虽然计算高效，但在以下方面与真实接触有差异：
- 真实的接触发生在微小的粗糙峰（asperity）上，是多点接触；仿真中是点或面接触。
- 真实的摩擦取决于表面微观形貌、湿度、温度；仿真中是一个标量系数。
- 真实的碰撞有能量耗散（通过材料变形、热耗散）；仿真中用恢复系数（restitution）简化。

**（2）质量、惯量与几何参数不准确**

机器人的 CAD 模型可以导出每个 link 的质量和惯量，但真机上存在误差来源：
- 电缆、连接件、螺丝等小部件未在 CAD 中建模。
- 材料密度有制造公差。
- 磨损和变形改变了质量的原始分布。
- 物体的真实质量和仿真中设定的质量可能完全不同。

**（3）执行器动力学差异**

仿真中的执行器几乎总是被简化为理想力矩源或理想位置源。真机上的执行器会引入：
- **响应延迟**：从控制指令发出到电机实际输出力矩，有一个不可忽略的时间差（几毫秒到几十毫秒）。
- **传动非线性**：减速器有齿隙、摩擦和弹性变形。
- **力矩限制**：真实电机的力矩-速度曲线不是恒定值——高速下可用力矩降低。
- **反电动势**：电机在被动运动时会产生反向电压，影响实际力矩。

**（4）传感器噪声与延迟**

仿真中，关节编码器的读数是真值（无噪声）。IMU 的输出是完美角速度和加速度。物体的位姿可以直接从仿真状态中读取。真机上：
- 相机有噪声、运动模糊、曝光问题。
- 深度传感器在物体边缘、反光表面、远距离处产生误差。
- IMU 有零偏漂移和随机游走。
- 所有传感器都有通信延迟——你读到的数据是"几毫秒前的世界"。

**（5）通信与控制延迟**

仿真中，传感器读取 → 控制器计算 → 执行器响应的延迟可以设为零。真机上，这个闭环延迟（从传感器采样到执行器响应）可能是 5-50 ms。对于高频控制（如 1 kHz），50 ms 意味着 50 个控制周期的滞后——这足以让一个高增益控制器失稳。

**（6）视觉与感知的域差距**

如果任务涉及视觉（通过相机观测），Sim2Real gap 更大：
- 仿真渲染的图像在光照、纹理、材质上永远与真实图像有差异。
- 真实相机有镜头畸变、渐晕、白平衡偏移。
- 深度图在仿真中是完美的（每个像素都有深度值），真机上有空洞和噪声。

### 3.9.3 真机对照实验：SO101 reach

如果条件允许，本讲建议做一个最简单的 Sim2Real 对照实验：在 SO101 真机上跑 reach 任务，在 MuJoCo 中跑同样的 reach 任务，对比结果。

| 对比项 | 仿真 reach | 真机 reach | 可能的差异原因 |
|---|---|---|---|
| 末端最终误差 | < 2 mm | 3-8 mm | 电机延迟、齿隙、标定误差 |
| 轨迹平滑性 | 平滑 | 有微抖动 | 传动摩擦、结构弹性 |
| 执行时间 | 2.0 s | 2.3-2.8 s | 加速/减速段更长 |
| 停止超调 | 无 | 偶有 1-2 mm | 位置控制器的 overshoot |
| 可重复性 | 100% | 95-98% | 温度、摩擦力变化 |

做这个对照实验时，**安全注意事项**是必写内容：
- 使用低速、小范围的运动（关节速度限制在安全值以下）。
- 有人始终在旁看护，手放在急停按钮附近。
- 不直接运行未经检查的 AI 生成的真机代码——先仿真验证，再人工审查，最后低速上真机。
- 首次在真机上运行前，确保运动轨迹的每个 waypoint 都在工作空间内且远离碰撞边界。

### 3.9.4 缩小 Sim2Real gap 的常用策略

虽然 Sim2Real gap 无法完全消除，但有很多策略可以缩小它：

1. **Domain Randomization**（域随机化）：在训练时，故意随机化摩擦系数、质量、控制延迟、观测噪声等参数。这样训练出来的策略已经在"各种可能的世界"中见过面，对真实世界的不确定性有更好的鲁棒性。这是目前缩小 Sim2Real gap 最有效的策略之一。

2. **System Identification**（系统辨识）：通过实验测量真机上的质量、摩擦、阻尼、延迟等参数，然后在仿真中设置相同的值。这需要一定的实验条件（如用六维力传感器测量惯性参数），但能显著缩小差距。

3. **Domain Adaptation**（域适配）：使用少量的真机数据（几百到几千条）对仿真训练的策略进行微调，让策略适应真实世界的数据分布。

4. **Progressive Training**：从理想仿真开始训练，逐步加入随机化和真实约束，让策略平稳过渡。

5. **Sim-friendly 设计**：在真机上选择与仿真兼容的传感器和控制器模式。例如，如果仿真中用的是 PD 位置控制，真机上也尽量用同样的控制模式（而不是切换到力矩控制），以减少控制接口差异。

**本节小结**：Sim2Real gap 不是屏障，而是需要被理解和管理的客观存在。它的六个主要来源——接触模型、参数不准确、执行器差异、传感器噪声、控制延迟、视觉域差——各自贡献了一部分差距。理解这些差距不是为了消除仿真（仿真仍然是不可替代的），而是为了知道什么时候可以信任仿真结果、什么时候需要上真机验证、以及如何用 domain randomization 等策略缩小差距。

## **3.10 实验闭环：记录、失败复盘、AI 辅助验证和作业交付**

既然仿真和真机都会失败，最后一节要教学生如何记录、复盘，并把失败变成下一次实验。

### 3.10.1 统一实验记录表

每次实验（无论成功或失败）都应记录在统一格式的表格中。这方便后面做对比和总结：

| 字段 | 说明 | 示例 |
|---|---|---|
| 任务名称 | reach、pick-place、standing、walking、turning | reach |
| 平台 | MuJoCo、Isaac Lab | MuJoCo |
| 机器人模型 | 使用的机械臂或 G1 模型 | UR5 + Robotiq 2F-85 |
| 观测 | 关节、末端、物体位姿等 | joint_pos (6), ee_pos (3), target_pos (3) |
| 动作接口 | 关节控制、末端控制、速度指令 | joint position control (6) |
| 修改参数 | 改了什么，原值和改后值 | friction 从 1.0 → 0.3 |
| 成功判定 | 成功条件 | dist < 0.01 m |
| 失败现象 | 具体描述（不是"失败了"，而是"怎么失败的"） | 物体在抬升过程中从夹爪左侧滑出 |
| 验证方法 | 如何确认原因 | 改回 friction=1.0 重跑，不再滑出 |
| 下一步改进 | 基于本次实验的下一步计划 | 测试抓取不同质量物体的最小夹持力 |

### 3.10.2 失败复盘五步法

一次实验失败了，怎么从中提取有价值的信息？按照以下五步进行：

**第一步：现象——失败看起来是什么？**

用客观描述替代主观判断。不要写"抓取失败了"，写"抬升到 5 cm 时物体从夹爪中滑出并掉落在桌面上"。不要写"G1 摔了"，写"行走 3 秒后 base 向右侧倾斜，第 4 秒时右膝触地"。

**第二步：位置——失败最早出现在哪一环？**

沿着任务的时间线往回找，找到失败发生的第一个信号。如果物体在抬升时滑出，回看夹爪闭合瞬间的接触力——当时就夹住了吗？如果 G1 在第 4 秒摔倒，回看第 3 秒的脚步接触力——是不是右脚已经打滑了？

**第三步：原因——可能的原因是什么？**

列出至少两个可能的原因（而不是只认定一个）。例如：
- 原因 A：摩擦系数不足（friction=0.3），物体表面太光滑。
- 原因 B：夹持力不够大，夹爪未能产生足够的法向力。
- 原因 C：抬升速度太快，加速度导致的惯性力超过了摩擦力。

**第四步：验证——如何用实验确认？**

对每一个可能的原因设计验证实验：
- 验证 A：将 friction 改回 1.0，其他不变，重新跑。
- 验证 B：增大夹持力（如从 10 N 增加到 30 N）。
- 验证 C：降低抬升速度（如从 0.05 m/s 降到 0.02 m/s）。

只改一个变量，看结果变化。

**第五步：改进——下一次改什么？**

基于验证结果，确定下一步的实验方向。如果确认是摩擦系数的问题，下一步可能需要：
- 系统性地测试不同摩擦系数下的抓取成功率。
- 考虑更换夹爪的接触材料（真机上）。
- 在仿真中加入摩擦系数的域随机化（为将来的 RL 训练做准备）。

### 3.10.3 AI 辅助验证的使用边界

AI（如 ChatGPT、Claude 等大语言模型）在仿真学习中确实有用，但必须划定边界：

**AI 可以做的事情**：
- 解释 MJCF 文件中的字段含义（"`armature` 参数是干什么的？"）。
- 解释仿真器的报错信息（"MuJoCo 报 self-collision detected 是什么意思？"）。
- 帮助生成实验记录表的初稿（"帮我根据这几行日志整理成实验记录表"）。
- 帮助理解控制参数的物理含义（"Kp 从 1 变到 10 会对系统响应产生什么影响？"）。

**AI 不能代替你做的事情**：
- 判断实验结果是否正确——你必须自己跑实验、看录屏、验证。
- 代替你"脑补"实验中没有观察到的现象——AI 只能基于你给的信息推理，如果观察不全，推理就是空中楼阁。
- 直接生成真机运行代码——AI 输出的控制代码可能包含不安全的参数（如力矩过高、速度过快），必须在仿真中充分验证并由人审查后才能上真机。

**报告中必须遵守的原则**：区分"AI 建议"和"自己验证后的结论"。例如："AI 建议将 Kp 从 2.0 降到 1.0 来减少振荡，我验证后发现振荡确实减少，但稳态误差从 2 mm 增大到了 5 mm"——这和"我调了半天调不好"是完全不同的实验记录质量。

### 3.10.4 本讲作业交付清单

| 交付物 | 说明 | 最低要求 |
|---|---|---|
| MuJoCo reach 录屏 + 参数记录 | 跑通 reach，记录末端误差和轨迹 | 1 次成功 + 记录表 |
| MuJoCo pick-place 录屏 + 参数实验 | 至少改一个参数（摩擦/质量/频率），记录变化 | 1 次 baseline + 1 次改动 + 对比 |
| Isaac Lab 机械臂截图 + 接口解释 | 标注 observation、action、reward 分别对应什么 | 3 张截图 + 每张 2-3 句说明 |
| G1 locomotion 截图/录屏 + 指令记录 | standing/walking/turning 各一次，记录速度指令和跟踪效果 | 3 次实验 + 记录表 |
| 一份失败复盘 | 按五步法复盘一次你遇到的失败 | 完整的现象/位置/原因/验证/改进 |
| Sim2Real 理解说明 | 写一段话说明"为什么仿真成功不等于真机成功" | 引用 3.9 节中至少一个具体 Gap 来源 |

**作业评价的核心标准**：不是截图数量多不多、录屏好不好看，而是**理解和复盘的质量**。一份只有 5 次成功的作业，如果对每次失败都有清晰的复盘分析，优于一份 20 次成功但对失败避而不谈的作业。

**本节小结**：实验闭环是连接"会跑 Demo"和"会做实验"的关键环节。统一的记录格式让你能对比不同实验的结果；五步复盘法让你能从失败中提取经验；AI 辅助验证能提高效率，但最终判断必须基于你自己的观察和数据。本讲解决的是"任务如何进入仿真"；下一讲要解决的是"目标如何从真实感知中来"。

## **3.11 下节衔接：从仿真目标到真实感知与位姿估计**

### 3.11.1 本讲回顾

本讲从"为什么不直接上真机"开始，走完了一条从真实任务到仿真实验的完整链路：

1. 我们学会了用一个七问框架拆解任何仿真任务——目标、模型、场景、观测、动作、参数、判定。
2. 我们理解了 MuJoCo 和 Isaac Lab 各自擅长什么——前者让你看清任务骨架，后者让你理解环境组织和并行评测。
3. 我们在 MuJoCo 里跑了机械臂 reach 和 pick-place，在 Isaac Lab 里理解了 observation/action/reward 的设计逻辑，并在 G1 locomotion 中体验了运动任务的全身协调。
4. 我们讨论了为什么仿真成功不等于真机成功——Sim2Real gap 的六个来源。
5. 我们学会了记录实验、复盘失败、区分 AI 建议和自己验证的结论。

### 3.11.2 新问题：目标从哪里来？

在本讲的仿真实验中，目标点是直接赋值的：

```python
target_pos = np.array([0.3, 0.0, 0.2])  # 人工指定
```

在仿真中，这是合理的——我们先验证"如果目标已知，任务是否可行"。但真机上，没有人会用一个尺子去量目标物体的位置然后手动输入。真实系统的目标必须来自**感知**——相机看到物体，算法估计物体的 6D 位姿，然后这个位姿才成为操作任务的目标。

这引出了三个关键问题，它们构成了第 6 讲的核心：

1. **相机里的像素如何变成机械臂坐标系下的位置？**
   - 这需要相机标定（内参 + 外参）、深度图反投影、手眼标定（eye-in-hand 或 eye-to-hand）。

2. **物体在三维空间中的完整位姿如何估计？**
   - 这需要 6D 位姿估计算法——从传统的点云配准（ICP）到基于深度学习的端到端位姿回归。

3. **感知误差如何影响操作任务？**
   - 如果位姿估计偏了 5 mm 或 5 度，抓取成功率会受多大影响？真机实验中如何区分"控制失败"和"感知失败"？

### 3.11.3 过渡

> 本讲我们完成了任务进入仿真——我们看到了 robot、scene、object、observation、action、physics、success metric。下一讲要解决机器人如何知道目标在哪里——从像素到抓取位姿的完整感知链路。
