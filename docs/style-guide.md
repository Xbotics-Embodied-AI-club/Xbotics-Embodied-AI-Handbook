# 全书风格指南（Style Guide）

> **定位**：把 README「课程内容风格」、[`templates/lecture-template.md`](../templates/lecture-template.md) 与附录「教程实施原则」落成**可检查的约定**。  
> **适用**：`docs/` 正式讲稿；不含 `docs/superpowers/` 等写作过程文档。  
> **修订原则**：新稿按本文执行；旧稿按文末优先级逐步对齐。

---

## 0. 最高原则：讲清楚优先

**讲清楚 > 套模块。** 十模块与检查清单是**验收项**，不是正文必须拆成的十个空壳标题。

| 含义 | 说明 |
|------|------|
| **先讲透，再补齐外壳** | 概念、对比、必要公式可以写够；写完后再检查目标 / Demo / 作业 / 失败是否齐全 |
| **「理论够用」≠「少讲理论」** | 够用 = 学生做完本讲任务后，能解释「为什么这样做、错了怎么查」；不是故意砍背景 |
| **统一的是外壳，不是腔调** | H1、章首目标、双路径、作业与失败要齐；中间叙事可连贯（像 Part 3–4），不必每段都贴模块名 |
| **冲突时怎么判** | 为压行数、凑十节、少公式而导致读者看不懂 → **改回讲清楚**；格式问题往后排 |

写完自问三句（过不了就先改正文，再管格式）：

1. 读者能否用自己的话说明本讲在解决什么问题？  
2. 离开清单，能否讲清关键步骤背后的原因？  
3. 失败时，文中是否给了可执行的排查路径？

## 1. 一句话定位

这是一门**具身智能工程实践课**：任务驱动、概念讲透到能上手、实验可复现、失败可复盘。  
不是论文综述堆砌，不是纯科普，也不是作者写作提纲。

推荐叙事弧（弧线可伸缩，不可跳过「讲清」）：

```text
提出问题 → 讲清概念 → 跑通 Demo → 分析失败 → 完成作业
```

课堂时间结构参考附录（约 **30% 概念 · 40% Demo · 30% 调参/复盘**）。  
文稿里概念篇幅可以按讲次变：理论依赖重的讲次，概念段长于 30% 完全正常。

## 4. 讲次类型与篇幅（软参考）

在 Part 导言或讲稿元信息中标明类型，避免读者对「一讲」预期失真。  
下表是**量级参考**，不是硬上限；为讲清楚而超长，优先保留概念与对比，把安装日志、完整脚本外置。

| 类型 | 典型角色 | 量级参考（不含大段附录代码） |
|------|----------|------------------------------|
| **导论** | 开篇立概念、串起后续讲次 | 约 150–400 行 |
| **实战** | 主 Demo + 作业为主 | 约 400–900 行 |
| **概念 / 方法地图** | 位姿、VLN 理论等，需一张够用的地图 | 以「地图 + 本讲任务」够用为准；可长于综述旧预期 |
| **前沿扫盲** | 点到为止的路标 | 约 200–500 行；论文作路标，不代替本讲任务 |
| **答辩 / 综合** | 闭环验收与展示 | 以清单与评分表为主，可较短 |

**该外置的**：完整安装过程、重复命令块、超长配置。  
**不该为压行数砍掉的**：关键定义、必要对比、支撑本讲任务的公式与直觉解释。

## 5. 文件与目录约定

### 5.1 正式稿唯一真相源

- 读者可读路径以 [`docs/SUMMARY.md`](SUMMARY.md) 为准；**一讲只挂一个 `.md`**。
- 草稿、旧版、并行稿放入 `docs/_drafts/`（或同目录但**不得**被 SUMMARY 链接），文件名带日期或 `draft-` 前缀。
- 禁止在正式稿正文中保留作者内部批注，例如：`（问题：建议…）`、`待补充：从飞书…`、顶部「编辑意见」。

### 5.2 文件命名

| 规则 | 说明 |
|------|------|
| **新稿** | `NN-english-slug.md`（如 `06-pose-estimation.md`） |
| **已有中文文件名** | 可暂留（Part 3–4），但 SUMMARY / `meta/outline.yaml` 必须指向同一文件 |
| **禁止** | 同讲多份「正式感」文件并存且无主次说明 |

### 5.3 讲次 H1

统一为：

```markdown
# 第 N 讲：标题（可选副标题）
```

- `第` 与数字、`讲` 与冒号之间保留空格：`第 6 讲：…`（不要写成 `第6讲`）。
- H1 **不要**整行加粗（`# **第 5 讲…**`）。
- 每讲必须有且仅有一个 H1；不得从 `## 学习目标` 直接起笔。

可选元信息块（紧跟 H1，blockquote）：

```markdown
> **所属部分**：第二部分：机器人视觉操作  
> **讲次类型**：实战 / 导论 / 概念地图 / 前沿 / 答辩  
> **前置依赖**：第 4 讲、第 5 讲  
> **关联代码**：[`code/lecture06/`](../../code/lecture06/)
```

## 6. 章节结构：外壳统一，正文可叙事

### 6.1 推荐编号（外壳）

Web 正式稿推荐：

```text
# 第 N 讲：…
## N.1 本讲目标
## …（中间：按讲清楚需要组织，可用 N.2 / N.3… 或叙事小标题）
## 作业交付          ← 章末可扫读
## 常见失败与复盘    ← 章末可扫读
## 关联代码
```

完整十模块顺序见模板，适合**新开空白讲**时当提纲。已有强叙事的讲次（尤其 Part 3–4）**不必**改成十个一级节；把必达信息嵌进正文，并在章末用小标题扫读即可。

章首模块名称统一为「本讲目标」（`N.1`），不要混用「本讲提要」「学习目标」。

**不要**把下列形态当作正式读者结构：

| 形态 | 原因 |
|------|------|
| `## **一、本讲目录**` / `## **三、写作框架**` | 作者提纲 |
| 仅有 `# 1` / `# 2` 且无「第 N 讲」H1 | Web 导航弱 |
| 为凑齐 N.1–N.10 而把连贯解释拆成空壳节 | 伤害「讲清楚」 |

### 6.2 必达信息（验收，不是目录强制）

下列信息必须在文中**找得到**（可合并、可嵌入叙事）：

| 必达信息 | 最低要求 |
|----------|----------|
| 本讲目标 | 「能回答」+「能完成」；目标要具体到本讲任务 |
| 本讲任务 | 一个具体任务名 + 为何选它 |
| 概念主线 | 学生能复述的一条主线（可用 ` ```text ` 框）；理论章还要有够用的方法地图 |
| 双路径 | 有硬件 / 无硬件各至少一条可执行路径（无真机则显式声明替代） |
| 实验或 Demo | 最小可跑通闭环 |
| 作业交付 | 产出物清单（格式 / 命名） |
| 失败复盘 | 至少 3 条「现象 → 可能原因 → 怎么查」 |
| 关联代码 | 指向 `code/lectureNN/`（无则说明替代入口） |

### 6.3 Quarto / PDF

- 推荐 Web 正式稿与 PDF 导出源分离，避免读者先看到大段 YAML。
- 若暂时同文件：可保留 YAML，但须有 `# 第 N 讲：…`；小节尽量带讲次号。
- Pandoc 属性（如 `{width=50%}`）可保留供 PDF。

## 7. 语气与写法

### 7.1 推荐

- **读者导向**：把「你要完成什么」说在概念前面或紧跟着说清。
- **设问开场**：点出本讲要解决的工程矛盾。
- **先主线、再展开**：用短 ` ```text ` 框给出 3–7 步，再深入。
- **跨讲衔接**：符号与称呼前后一致。
- **失败与成功同等重要**。

### 7.2 避免（含「过度执行风格」）

| 避免 | 说明 |
|------|------|
| 只有论文名 / 只有清单，没有解释 | 读者无法建立模型 |
| 堆术语却接不上本讲任务 | 「显得专业」但用不上 |
| 纯 bullet 提纲代替正文 | 提纲可以作目录，不能代替讲解 |
| **为套模块而拆碎好叙事** | 连贯讲清楚优先 |
| **为「理论够用」删掉必要直觉与对比** | 删完学生只会抄命令 |
| 口语过碎、网络梗过多 | 影响投影与印刷 |

### 7.3 概念地图类章节（位姿、VLN 理论等）

这类讲次**允许、也常常需要**比实战章更多的概念篇幅。约束目标是「有任务锚点」，不是「每格只写两三句」。

1. 开篇写清**本讲最小任务**（哪怕只是跑通一个评测 / 标定检查）。
2. 方法地图用总图或表格；每个格子写清「是什么 / 何时用 / 和本讲哪一步有关」——篇幅以读者懂为准。
3. 公式：本讲任务用到的，定义清楚并给直觉；用不到的外链，勿为炫技展开。
4. 章末回到：「你现在能检查什么、怎样算做完」。

## 8. 术语与中英混用

- **正文中文**；专有名词可保留英文，**首次**给中文或一句解释。
- 缩写首次写全称，如「视觉语言动作模型（Vision-Language-Action, VLA）」。
- 与 [`meta/outline.yaml`](../meta/outline.yaml)、[Xbotics-Embodied-Guide](https://github.com/Xbotics-Embodied-AI-club/Xbotics-Embodied-Guide) 对齐；同义不要一讲一个叫法（切换时先定义）。
- 代码标识符、ROS topic、包名保持原文。

## 9. 代码与命令

| 约定 | 说明 |
|------|------|
| 完整工程 | 放 `code/lectureNN/`，文末「关联代码」链接 |
| 正文 | 放**关键片段** + 够初学者接上的**最小脚手架**（接口、易错命令、一小段完整可抄示例均可） |
| 不要 | 把正文变成安装日志墙；也不要「全文零代码、全扔仓库」导致读断 |
| 语言标识 | `python` / `bash` / `text` / `yaml`；禁止 `Plain Text` |
| 长环境配置 | 细节进 `code/.../README.md`；正文给最短路径与排错要点 |

安全相关命令须提示前置检查（见附录安全原则）。

## 11. 数学公式

- 行内 `$...$`，独立式 `$$...$$`；符号首次定义，跨讲沿用（如 $o_t, a_t$）。
- **为讲清楚所必需的推导与直觉，写在正文**；超过一页的纯代数展开可放附录，但正文须留下「结论 + 为何重要」。
- 不要为删公式而删懂法；也不要堆与本讲任务无关的证明。

## 12. 交叉引用与资源

- 写「第 N 讲」+ 可选节号，尽量可点击。
- 开源链接汇总 [`references/links.md`](../references/links.md)；讲内短列表即可。
- PDF 与正式 md 同源或可追溯，避免长期分叉。

## 13. 发布前检查清单（PR 自检）

**先内容，后格式：**

- [ ] §0 三问能通过：问题清楚、原因清楚、排错路径清楚
- [ ] 没有为凑模块 / 压行数而删掉必要概念与对比
- [ ] SUMMARY / outline 指向本文件；无同讲第二份正式稿
- [ ] 仅有一个 H1：`# 第 N 讲：…`；有「本讲目标」（能回答 / 能完成）
- [ ] 写清本讲任务；双路径齐全或显式声明
- [ ] 有作业交付 + 至少 3 条失败复盘
- [ ] 无「问题：」「待补充」等内部批注
- [ ] 配图路径与 caption 符合规范（或已登记迁移例外）
- [ ] 代码块语言规范；完整工程在 `code/lectureNN/`（正文保留必要脚手架）
- [ ] 术语与前后讲一致；外链图已本地化

## 14. 反例速查

| 反例 | 应改成 |
|------|--------|
| 十个空壳 `N.1`–`N.10`，中间没有讲透 | 连贯讲清楚，章末补作业 / 失败 |
| 为「理论够用」删掉定义与对比，只剩命令 | 补回直觉与「为何」；命令可外置 |
| `# **第 5 讲**` + `## **一、本讲目录**` | 标准 H1 + 读者章节 |
| 正式稿残留编辑意见 | 删除后再发布 |
| SUMMARY 链到 A，磁盘只有 B | 改链接或重命名 |
| 只有 survey，无任务锚点 | 补最小可运行路径与作业 |
| 正文 200 行安装日志 | 移到 `code/.../README.md`，正文留最短路径 |
| 三套图片目录混用 | 统一到 `assets/figures/lectureNN/` |

## 15. 旧稿迁移优先级

1. **P0**：断链、多稿定主、删除正式稿内批注。  
2. **P1**：补齐「讲清楚」缺口（任务锚点、必要概念）+ 章首目标 / 章末作业与失败。  
3. **P2**：H1 与编号外壳、配图路径与 caption、Quarto 与 Web 分离。  
4. **P3**：图标、历史文件名英文 slug 化等细枝末节。

对齐格式时**不要**顺手砍掉已有的清楚讲解。

## 16. 维护

- 风格争议：先看是否违反 §0；再以样章（§3）仲裁；仍不定则改本文并在 PR 说明。
- 修改本文后：同步检查 README「课程内容风格」摘要与 `CONTRIBUTING.md` 链接是否仍准确。
