# 第一、二讲写作风格改写设计

## 目标

在不改变课程知识范围、教学顺序、技术事实和实验要求的前提下，重写第一讲与第二讲的正文表达，使其兼具教材的严谨性和 Datawhale 技术文章的问题牵引式可读性。

改写文件仅限：

- `docs/part1-system-basics/01-introduction.md`
- `docs/part1-system-basics/02-ros2-architecture.md`

## 参考文章的共同风格

三篇参考文章虽然主题不同，但共享以下写法：

1. 用热点、场景、数字、反差或反直觉判断迅速提出问题；
2. 用连续追问建立阅读动机，再给出一句话定义或核心判断；
3. 按“是什么—为什么—如何运作—有什么边界—意味着什么”推进；
4. 用短段落、类比和“不是……而是……”式对比解释技术概念；
5. 用案例、数据、流程或失败模式支撑判断，不依赖空泛结论；
6. 在阶段结尾提炼一句能够被记住的判断，并自然引向下一节；
7. 同时说明机会、限制和风险，避免只介绍优势；
8. 保留必要的英文术语、来源、代码和专业细节，但先给读者直观理解。

## 总体改写策略

采用“叙事化重写”，而不是简单润色或媒体化重构。

每个主要小节优先使用以下叙事单元：

```text
真实场景或关键疑问
        ↓
一句话核心判断
        ↓
机制与组成部分
        ↓
案例、流程、表格或代码
        ↓
边界、误区与风险
        ↓
阶段结论与下节过渡
```

该顺序是表达原则，不要求所有三级标题机械套用相同模板。短小知识点可以合并叙述，实验步骤、命令和检查表继续采用结构化格式。

## 第一讲改写设计

第一讲的核心矛盾是：AI 已经很会“回答”，为什么机器人仍然很难把事情“做成”？

改写以“从数字世界走进物理世界”为叙事主线：

1. 开头先呈现“说得对”和“做得成”的反差，快速建立具身智能的问题意识；
2. 定义具身智能时，先用一句话说明身体、环境和反馈为什么不可缺少，再展开七个组成部分；
3. 解释系统闭环时，持续使用“把红色杯子放到托盘”这一任务，让抽象模块对应具体动作；
4. 比较传统 Pipeline、模仿学习、强化学习、VLA 和世界模型时，强调它们分别解决什么问题以及不能单独解决什么；
5. Demo、作业和总结继续服务于“亲手看见闭环”，不扩写算法细节；
6. 每个主要章节形成明确判断，并用过渡句连接下一张系统地图。

## 第二讲改写设计

第二讲的核心矛盾是：模型能够预测动作，为什么仍然不等于拥有一个可工作的机器人系统？

改写以“让单个模型进入可靠系统”为叙事主线：

1. 开头从模型输出动作却无法稳定落地的场景切入，说明硬件、接口、通信、控制、安全和记录缺一不可；
2. 解释软硬件架构时，以“状态如何上行、指令如何下行”为主线，而不是罗列模块名；
3. 解释 ROS2 概念时，先说明各自解决的通信问题，再给定义、命令和本章案例；
4. 继续使用统一的六关节机械臂任务贯穿 Node、Topic、Service、Action、Launch、控制闭环和 episode 记录；
5. 对每类接口补充适用边界和常见误解，突出“消息发出不等于动作正确执行”；
6. Demo 与实验部分保持可操作性，增加必要的上下文和结果判断，但不改写为完整 API 手册；
7. 结尾从排错表收束到系统思维：真正可靠的不是某个模块，而是可观察、可验证、可恢复的闭环。

## 语言规范

- 优先使用主动语态和具体主语，减少“进行了”“实现了”等空泛表达；
- 长段落按一个中心判断拆分，避免连续堆叠概念；
- 问句用于建立问题或推进论证，不连续制造悬念；
- 类比必须帮助理解技术机制，不使用会损害准确性的夸张比喻；
- 可以使用“先说结论”“换句话说”“真正的问题是”等口语化连接，但控制频率；
- 保持教材语气，不使用“炸裂”“颠覆”“天价”等营销化词汇；
- 英文术语首次出现时给出中文解释，后文保持称呼一致；
- 表格、代码块、命令、路径、Topic 名称和字段名保持技术精度；
- 不虚构数据、案例、论文结论或项目能力。

## 图片与并行线程隔离

- 不修改、生成、删除、移动或重命名任何图片文件；
- 不修改现有图片路径、图号和图注；
- 不修改图片线程使用的 `.worktrees/lecture-visual-polish`；
- 文字改写仅在 `codex/lecture-text-style` 分支的独立 worktree 中进行；
- 图片线程产生的新图片和图片引用调整不自动带入文字分支，最终整合时单独处理；
- 忽略主工作树中的 `.crdownload` 临时文件，不读取、不删除、不提交。

## 保留与允许调整的内容

必须保留：

- 两讲现有一级、二级章节的知识范围和教学顺序；
- 图片引用、图片编号与图注；
- 代码逻辑、命令、接口名、路径和安全边界；
- Demo、实验、作业、排错与参考资料；
- 第一讲的课程地图定位和第二讲的统一机械臂案例。

允许调整：

- 段落顺序和句子结构；
- 三级标题措辞，但不改变其知识归属；
- 重复内容的合并与过渡句的补充；
- 开场、案例引入、阶段总结和章节衔接；
- 为解释清楚而增加的短类比或反例。

## 验收标准

### 内容

- 第一讲围绕“会回答不等于做得成”形成连续叙事；
- 第二讲围绕“模型不等于系统”形成连续叙事；
- 原有知识点、实验要求和安全边界没有遗漏或实质改变；
- 每个主要小节都能回答一个清晰问题，并产生明确结论；
- 重复定义、重复结论和机械式小结明显减少。

### 风格

- 开头能在较短篇幅内建立问题、反差和阅读动机；
- 专业概念先有直观解释，再有术语、机制和细节；
- 段落长度与句式有节奏变化，避免大段平铺直叙；
- 口语化服务于理解，不损害专业性；
- 风格来自三篇样本的共同特征，不复制其特定句子或主题表达。

### Markdown 与隔离

- 两个文件各自只有一个一级标题，标题层级连续；
- 代码围栏成对闭合，表格列数一致；
- 所有原有本地图片引用完整保留；
- Git 差异中不出现图片、其他章节、代码或配置文件；
- 提交前对图片引用、标题结构、代码围栏和改动文件清单执行自动检查。

## 范围外内容

- 制作、替换或优化图片；
- 调整其他章节、目录、课程大纲或代码工程；
- 核查并更新所有外部技术资料的时效性；
- 为追求媒体化效果而删减核心知识或安全说明；
- 将参考文章中的事实、案例或观点移植到教材中。
